# 实况视频与静态封面的色彩一致性（工作区修复，未发布）

## 反馈与实际证据

用户报告 Windows 自带“照片”播放最终实况 JPG 时，视频略灰、静态封面正常。对用户明确指定的文件只读分析，原文件前后 SHA256 相同；私有媒体、路径和诊断报告仅保留在忽略目录，不提交。

该文件的 JPEG 有 sRGB ICC；内嵌 H.264 视频的 MP4 `nclx` 和码流 VUI 均为 BT.709 色域、BT.709 传递函数、BT.709 矩阵、有限范围（1/1/1，full-range flag=0），未发现容器/码流范围标签冲突。按 XMP 精确对应首帧：

- 采用现有参考显示策略（理想黑位 gamma 2.4）转 sRGB 后，与封面缩小至相同尺寸比较，RGB 平均绝对差约 **0.625/255**。
- 仅做矩阵/范围转换、不做对应传递函数转换时，差约 **10.106/255**，整体更亮。

这些是文件和像素分析，**不是 Windows“照片”渲染管线的测量或内部实现证明**。

制作同一封面、同一前三秒/180 帧时序、AAC-LC 44100Hz 双声道的 A/B 实况：A 保持原 BT.709 编码，B 实际转换至 sRGB 传递函数并标记为 1/13/1。B 的矩阵/范围解码与封面平均差约 **0.867/255**。两份封面保留相同压缩图像及 ICC 字节，原文件不变。

用户明确反馈：**手机上 B 正常，A 略发灰**。该反馈限于这份短片和该手机；手机型号未记录，也不能据此宣称所有手机或 Windows“照片”均已验收。

## 实现范围

- `video-processing.ts`：保留供封面使用的 BT.709 中间表示默认值。只有重新编码的实况视频选择 sRGB 输出，在高精度空间处理之后、8-bit/4:2:0 量化之前，执行实际传递函数转换。
- `encode-export.ts`：手动编码和“原画质（跟随原片）”均使用此转换；H.264/MP4 标记为 BT.709 色域、IEC 61966-2-1（sRGB）传递函数、BT.709 矩阵、有限范围，并验证输出元数据。
- 不只是修改标签，不增加饱和度/对比度，不改变封面转换策略，也不对封面重复做 gamma 转换。
- HDR 仍须明确同意并先走既有 HDR→SDR 映射。已是 sRGB 的输入必须避免重复变暗。
- 严格压缩码流复制路径不改写色彩或像素。原画质预设是高保真重新编码，不是该严格复制路径。
- 源 PTS、封面关联、FPS/VFR/旋转、音轨选择及 AAC 采样率/声道策略保持原约束。新增转换仅在导出执行，不增加交互阶段媒体工具启动。

## 回归门槛

- 独立生成字节准确的有限/全范围 YUV 灰阶及彩色色块，依数学 BT.709 矩阵、gamma 2.4 和 sRGB 方程计算期望；另测已是 sRGB 的输入。
- 手动模式与原画质预设均封装最终 JPEG，再提取其内嵌视频，核对真实像素、JPEG ICC、MP4 `nclx` 和 H.264 VUI（1/13/1，有限范围）、源不变、帧数/PTS/时长及显式无声。
- 码值允许差为 4/255（均匀色块内部的 YUV 量化/CRF16/JPEG94 预算）；原先中灰约 10 以上的 gamma 偏差不能通过。既有封面数学断言和视频首帧精确哈希断言不降低。
- 桌面保存测试从最终 JPEG 取出 MP4，同时检查灰块与封面一致及实际 523Hz AAC 音调，不能只检查预览或是否存在音轨。
- 保留既有 HDR 同意、精确时间、取消清理、音频及严格复制回归。
