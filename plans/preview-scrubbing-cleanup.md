# 视频预览、拖动定位与缓存清理改进计划

## Context
- 用户反馈：频繁加载素材；拖动左右裁剪手柄时希望主预览显示对应帧；播放指针拖动中偶尔冻结、松手才更新；参考 `样本/参考代码/filmcraft/` 的播放实现；启动反复出现旧任务目录未清理警告。
- 当前仅做只读调查与计划，不修改实现、不启动会写入缓存的应用或测试。
- 用户确认：需要类似剪映/PR 的拖动中实时帧反馈，流畅优先，可用低清交互帧；不能只在松手后刷新。默认延续现有暂停定位行为，本轮不新增音频擦洗。
- 初步发现：`Editor.tsx` 使用原片或分段代理预览及下一段预取；`approximateSeek` 仅在当前预览区间内更新 video，区间外只移动指针；松手才走原生精确取帧。
- `Timeline.tsx` 的裁剪手柄目前只更新选区，不触发预览定位；播放指针才有拖动/松手定位回调。
- 警告来自 `main/jobs/temp-files.ts`。只读检查发现当前 `%APPDATA%/Motion Photo Studio/media-sessions/` 下有一个 `job-4abf6418-48c5-4fed-ab66-7b1665a619cc`，内有 1 个代理 MP4、8 个缩略图，但 `.owner.json` 已缺失；`jobs/` 为空。这证实本机反复警告至少有一项来自无标记残留，而不是每次都在加载新任务。
- `remove()` 验证标记后直接递归 rm 整个目录；若标记先被删、媒体文件因占用删除失败，后续启动就再也无法验证所有权。这是与现象吻合的代码风险，尚不能证明该历史目录就是这样产生的。
- `MediaResources.revoke()` 仅调用 stream.destroy，不等待 close；紧接着删除目录有 Windows 文件句柄尚未释放的竞争窗口。

## 架构决策（按审阅反馈修订）
- 用户已选择 **原生常驻引擎**，并明确本阶段只面向 **Windows x64**，不做 macOS/Linux 或跨平台抽象。本次是预览架构重构，不再仅修补旧的 3/12 秒分段代理。
- 用户已授权安装 Rust；优先走 Rust + Windows API。若工具链经合理排查确实不可用，可按用户授权退到 C++ + 同一套原生协议/MF 架构；不是因为当前没装就放弃 Rust，也不降级成 Python/Node 调用 FFmpeg 抽帧。
- 自研时间轴时钟、解码调度、帧缓存与呈现；复用 Windows 成熟解码器，不从零实现 H.264/HEVC 算法。filmcraft 的 Windows 路线也使用 Media Foundation + D3D11/DXVA（`crates/platform/README.md`）。
- 采用 **Rust 独立辅助进程 + Media Foundation + Electron Canvas**；不采用 Electron 原生 addon 或 WebCodecs 主路线。操作系统解码能力不足时，在导入阶段准备兼容编辑素材，不在拖动时启动 FFmpeg。

```text
本地文件 → 导入准备：ffprobe 信息/索引 + 原生能力探测
                     └ 不兼容时 FFmpeg 一次生成编辑资源及 PTS 映射
                              ↓
Electron 时间轴 → 原生常驻预览进程 → 有界帧缓存 → Canvas 主预览
                    └ 音频解码/播放时钟与视频同步
                              ↓ 只保存剪点/源帧标识/参数
导出输出预览或成品 → 原片 + FFmpeg/Sharp → 既有校验/安全发布链路
```
- “编辑不调用 FFmpeg”涵盖播放、暂停、拖指针/手柄、逐帧、时间轴缩略图、选择视频封面；导入准备完成后这些操作的 FFmpeg/ffprobe **新增启动次数必须为 0**。
- “预览输出”是现有导出渲染流程，仍可调用 FFmpeg；离线自检同样独立于交互预览。不能把每次 seek 的转码改名为导入来规避边界。

## Approach

### 1. 统一拖动交互，主预览实时跟随
- `Timeline` 为播放指针、左手柄、右手柄提供统一 begin/update/end/cancel 生命周期；手柄更新选区后，用**约束后的实际边界**定位，不使用未限制的鼠标时间。保留现有抓握偏移、pointer capture、键盘、缩放和平移规则。
- 开始拖动即暂停；时间轴立即响应、主预览持续出帧，不等待 pointerup。松手由**原生引擎**完成最终源帧定位，保持暂停，不再调用 `media.frame → FFmpeg`。取消/失去捕获时结束交互状态，不留下后台循环。
- 右手柄的 `endUs` 仍是排他剪点；确认画面显示剪点之前最后保留的一帧，时间字段保留剪点本身。按真实 PTS 判断，不使用平均 fps 减一帧；左手柄沿用首个 PTS ≥ startUs 的定位语义。
- 区分目标时间、解码时间、实际显示时间和源帧标识。兼容代理可以精确对应源帧位置，但不是原片全分辨率画面，必须明确标注。
- “使用当前帧”固定原生引擎确认的源 PTS，并生成仅供界面使用的静态预览；最终 JPEG 仍由已有 `prepareFrameCover` 在导出阶段从原片该 PTS 重解码，绝不拿低清预览做成品。

### 2. 原生常驻引擎：解码、定位、缓存与音视频时钟
- 新建 `native/preview-engine/` Rust 工程，产物 `motion-preview.exe`。每个应用实例最多一个受管进程、一个活动素材会话；解码器与源读取器跨播放/seek 复用，关闭素材才释放，不随鼠标事件启动进程。
- 首版采用 **Media Foundation Source Reader** 负责系统支持容器的解复用与解码，减少从零实现 demux 的范围；启用可用的硬件解码/D3D11 路径，记录实际后端，不把“请求硬件”当成已验证硬解。无硬解时允许可用的系统软件解码；不支持的流进入导入兼容路径。
- Source Reader 的 seek 只作为定位起点：flush 旧世代样本，定位至目标前可解码位置，再向前解码，以样本时间与源帧索引选择目标；正确处理 B 帧呈现顺序、VFR、非零起点、尾帧。禁止把 seek 成功当作已经得到目标帧。
- 单独的控制循环持续接收最新目标；解码线程保留 **1 个活动定位 + 1 个最新待处理目标**。附近前进尽量续读，反向先查 GOP 邻域缓存，远跳再 flush/seek；合并重复请求，在可中断点切换，不每次移动重建解码器，不积压历史鼠标事件。
- 缓存键包含源指纹、会话世代、源 PTS、预览尺寸与色彩策略。解码帧缓存初始上限 256 MiB（含固定上限的在途/保留帧），保留当前帧和有限邻域；视频/音频输入队列另设字节与时长上限，不能按整片时长累积。按字节淘汰 LRU，驱动内部占用另外测量，不能宣称完全受应用预算约束。
- 优先级：松手确认/当前交互帧 > 正常播放需要的帧 > 邻域预取 > 缩略图。缩略图使用独立的低优先只读会话或空闲时解码，最多两个解码会话，不能改变前台解码器的位置。慢设备减少预取和预览尺寸，不阻塞鼠标。
- 引擎统一管理音频与视频：MF 解码所选音轨到 PCM，WASAPI 共享模式播放；有音频时按实际音频播放时钟调度视频，静音/无音轨时用单调时钟。暂停/seek 清空旧音频、重置世代；拖动时静音；设备切换/音轨切换不播放旧位置声音。首版不增加变速和音频擦洗。
- 临近时间连续解码和帧缓存是本次流畅性的基础，不依赖反复生成短 MP4。原生模块失败必须上报并终止会话，可重新打开；不偷偷回退到旧的逐次 FFmpeg 抽帧。

### 3. 导入准备、源 PTS 与跨进程呈现
**导入资源**
- 导入阶段执行 ffprobe 元数据/帧索引与原生能力探测。索引保存原片整数 PTS/timeBase、duration、关键帧和顺序，流式落盘/分页读取，避免大型素材整个索引塞进 JS 内存。不要根据平均 fps 推算源帧编号。
- 可直接解码的素材不转码；允许索引准备时先显示已有画面，并明确“正在准备帧索引”，尚未验证的源帧定位不能标成精确确认或用于封面。准备任务由导入触发一次，可取消；拖动不新建准备任务。
- 不支持的容器/编码、需要确定性 HDR→SDR 处理等，在导入阶段由 FFmpeg 一次生成**覆盖整条素材的可随机访问编辑资源**，采用短 GOP、受控预览尺寸；保留一源帧对应一代理帧及 VFR 时序，不沿用旧 `fps=30` 丢帧方案。准备完后统一读取，不能回到 3/12 秒窗口按需编码。
- 建立并核对代理样本与源 PTS 映射；MF 100 ns 时间戳、容器 edit list 与原片 timeBase 必须经过映射验证，不只用固定 offset 猜。无法唯一映射时明确失败，不伪造帧精确性。
- 展示准备进度/取消和实际兼容状态。兼容素材初版允许等待完整准备后编辑；这是移除编辑阶段转码的明确取舍，不承诺所有素材秒开。原片支持时优先直读。
- 编辑资源不受旧“两段代理缓存”规则淘汰。准备前检查剩余磁盘、边生成边检查应用缓存总预算（初始 2 GiB，保留安全余量），超限停止并提示，不能静默截断视频；确需提高预算时由用户确认。会话内复用，关闭后安全清理，不默认建立永久媒体库。
- 保持 HDR 明确同意、旋转、SAR 和色彩信息；主预览是源画面/兼容源画面加现有裁剪框，不冒充最终导出效果。

**IPC 与显示**
- 主进程管理辅助进程生命周期；stdin/stdout 使用版本化、长度前缀的控制消息与二进制帧协议，stderr 仅日志。消息包含 sessionId、generation、requestId、frameId、PTS、尺寸/stride/像素格式；限定消息长度、队列长度和像素乘积，拒绝损坏数据。二进制路径固定且校验，素材路径仅来自主进程受信选择/已验证的缓存。
- 主进程验证后，经受控 preload 帧事件交给 `PreviewSurface.tsx` 的 Canvas；预览像素帧初始最长边 960、拖动可降至 640，画布稳定挂载，不再用更换 video.src 驱动编辑定位。通过帧序号确认实际绘制，最多 2 帧等待 UI 消费，有背压并丢弃过时显示帧。
- 首版使用有界二进制像素传输，不用逐帧 JPEG 文件/base64，不承诺 GPU 零拷贝；GPU 读回、管道、Electron IPC 与 Canvas 的复制成本必须纳入原型测量。不在 React state 中保存每帧大数组，数据与绘制放 ref/独立控制器。
- `preview-controller.ts` 管理交互世代和请求合并；Canvas 保留最后有效画面直到新帧实际画出，局部展示准备状态。松手确认/换素材后，旧帧与旧音频绝不能回写。原生绘制回执驱动 displayed PTS，不能仅因发出 seek 就更新“已显示帧”。
- 常驻进程必须检测父管道断开并退出；close/shutdown 先停止任务、释放 MF/WASAPI/文件句柄并回执，再清理目录。超时可终止受管子进程，等退出后重试清理，不能结束同名的其他进程。

### 4. filmcraft 可借鉴部分与边界
- `样本/参考代码/filmcraft/crates/ui-egui/src/frames.rs`：缓存键含 target/frame/size/revision/draft；当前帧优先、预取次之、缩略图最低；缓存/排队/在途请求去重。
- `.../panels/monitor.rs`：分别记录请求帧和已显示帧，目标未就绪时保留缓存画面；播放采用预取与有限预滚。
- `.../panels/trim_monitor.rs`：裁剪边界也按当前媒体时间异步请求帧，不仅更新选区数字。
- `.../crates/platform/README.md`：Windows MF/D3D11、硬件能力探测、软件回退及故障处理。借鉴其常驻会话和明确回退边界；本项目首版选择 Source Reader + 系统解码/导入兼容资源，不直接搬用其完整样本级 demux、自研软件 codec 和 GPU 合成管线。
- 用户已确定原生路线，目标是**常驻解码会话 + 帧索引 + 预取/缓存 + 独立呈现**；不再将“只学调度、不动引擎”作为边界。不复制界面资产；如实现阶段实际复用代码，先审查对应许可与署名要求。

### 5. 修复安全清理与可解释告警
- `MediaResources` 增加可等待的 revoke/drain：先停止新读流，销毁并等待所有现存流 close。原生引擎也必须关闭素材并释放句柄后，才删除编辑资源；会话关闭、替换、退出统一遵守。等待有界，失败保留文件及所有权并报告，不无限挂住退出。
- `TempFiles.remove` 改为先验证拥有权及路径，再删目录内容，最后删 `.owner.json` 和空目录；不跟随符号链接/junction。对 Windows 占用做有限重试，仍失败时保留标记。
- 借鉴 `Publications` 的持久恢复记录模式：仅对已通过验证的 job 记录清理意图，绑定根目录与 job ID，不接受渲染端路径；直到目录完整删除才移除记录。处理“标记已删但空目录尚未删”的退出窗口；异常内容/失配时拒绝清理，不能据记录认领未知有内容目录。
- `create` 在写标记失败时，仅回滚本次实际创建且确认安全的空目录；不能误删已存在路径。启动恢复兼容现有有效 v1 标记。
- 用结构化结果区分缺少/损坏标记、占用、权限及异常路径，聚合数量并在“帮助与检查”展示原因及任务目录标识；当前处理失败仍显著提示。无所有权历史残留使用可收起的非阻断提醒，保留可查记录，不静默当作清理成功。
- **本机现存无标记目录不自动删、不补造标记。** 提供人工核查指引；若用户要实际清理，单独确认目录和操作后再执行，不包含在本计划的自动迁移中。

### 6. 原生构建与渐进切换
- 先做 Windows x64 原型门槛：打开实际 H.264/HEVC、连续播放音视频、拖动定位、源 PTS 对齐、960/640 像素跨进程显示、关闭释放文件。测量成功后再接入全部 UI；若系统能力或传输性能不达标，停止并报告具体证据，不回到旧 FFmpeg 拖动方案冒充完成。
- **先安装开发环境（已获用户授权，计划批准后执行）**：使用官方 rustup 安装用户级 `x86_64-pc-windows-msvc` 工具链与 rustfmt/clippy，记录并固定实际版本；校验下载来源，遇到证书/完整性异常停止，不使用来历不明镜像，不关闭安全验证。只做所需用户级 PATH 配置，复用现有 VS/SDK，不重装整个 Visual Studio。
- 已只读核实 `C:/Program Files/Microsoft Visual Studio/2022/Community` 安装了 `Microsoft.VisualStudio.Component.VC.Tools.x86.x64`，Windows SDK Include 目录有 `10.0.22621.0`、`10.0.26100.0`；还要以最小程序实际编译/链接确认工具可用，不能把目录存在当作构建成功。
- 开发依赖 Rust/MSVC/SDK；用户安装包**不要求安装 Rust、FFmpeg 或开发环境**。Rust 依赖固定版本/锁文件并审查许可证，helper 使用稳定协议，避免 Electron ABI 绑定。若证实 Rust 安装/链接持续不可用，记录原因再使用现有 C++ 工具链，保持架构与验收要求不变；不是转回子进程抽帧。
- helper 纳入 `resources/bin`，单独版本化完整性清单和启动握手（不能把它塞入要求恰好 ffmpeg/ffprobe 两项的旧清单而不迁移）。打包包含 exe、许可、版本信息；运行时不下载、不找系统 PATH 替代。
- 保留现有 FFmpeg/Sharp 导出引擎校验，分别显示预览引擎/导出引擎就绪状态。系统无 MF（如缺少 Media Feature Pack 的 Windows N）时明确阻断原生预览并提示环境要求；转换成 H.264 不能解决 MF 本身缺失，不做虚假回退。
- 原生原型阶段旧代码仅用于基线与开发对照；最终交付移除编辑调用链里的短窗口预览/单次抽帧，FFmpeg 工具仅保留给导入、导出、自检和测试。不留下静默自动退回旧路径的开关。

## Scope / Risks / Prerequisites
- 保留 Electron/React 界面、现有导出编码策略/原画质预设、原片、输出音轨选择和安全发布；本轮新增原生**预览**引擎，不移植 filmcraft 全部编辑模型，不自研视频编解码标准，不增加变速/音频擦洗。
- **工具链前置条件**：当前 PATH 和默认目录无 Rust；VS 2022 Community 的 x64/x86 C++ 组件与 Windows SDK 目录已发现，但尚未实际编译。用户已授权安装 Rust，批准计划后执行；计划期间仍不安装。若需额外提升管理员权限、重启或大范围修改系统组件，说明原因后再确认。
- Windows 编码器扩展、驱动、MF Source Reader 时间归一化、旋转和颜色转换有机器差异；必须通过原型和帧映射测试，不假定原生 API 天然帧精确。对无法建立可靠映射的素材明确阻断相关操作。

- 原生进程隔离是故障隔离，不是完整操作系统沙箱；路径授权、仅本地字节源、长度验证、有限资源和渲染端隔离仍必须落实。用户输入不得成为 shell 命令或任意打开路径。
